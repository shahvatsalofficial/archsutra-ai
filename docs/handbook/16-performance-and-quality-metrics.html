Performance and quality metrics

Measured speed, memory, test coverage and robustness checks, with the exact commands and caveats.

Version 0.1.2 · Source: docs/handbook/16-performance-and-quality-metrics.md

All numbers are measured, reproducible, and from a developer laptop (Windows 11), so absolute timings are pessimistic compared with Linux CI because of slower file-system access and antivirus scanning.

Speed and memory (synthetic repositories)#

Generated by node scripts/bench.mjs into docs/proof/benchmarks.md. Each case runs in a fresh process so peak memory is meaningful.

Speed on real repositories#

From docs/proof/realworld/results*.json (52 repositories, shallow clones): median 1.2 s per repository; typical small libraries under 0.5 s; the largest (5 000-file limit reached: django, webpack, prettier) take roughly 8 to 10 s on a quiet machine and up to 35 s when the machine is busy. Timings include reading files and all rules.

Bounds (why runtime is limited)#

The 15-second budget covers the directory traversal only; the rule scan after it is bounded by the file, size and byte caps. Truncation is always reported in the output ("TRUNCATED" and a blind-spot line), never silent.

Test coverage#

Node's built-in coverage over dist/ (report: docs/proof/coverage.txt):

MetricValue
Lines92.4%

Weakest areas: CLI argument-error branches and rarely used verify branches. CI prints coverage on every run; no minimum is enforced yet.

Quality gates in CI#

Typecheck (strict TypeScript), 31 tests on Ubuntu and Windows across Node 20, 22 and 24 (plus Ubuntu on the newest Node), structural verification of skills, agents, links and diagrams, a self-audit with --fail-on high, a production-dependency check, CodeQL, and (on pull requests) the DCO check. macOS is not in CI.
