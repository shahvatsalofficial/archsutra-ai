Testing and proof

Real, reproducible evidence: test results, CI matrix, labeled-fixture evaluation, sample outputs, and what is not proven.

Version 0.1.0 · Source: docs/handbook/08-testing-and-proof.md

Trust should be earned with evidence you can re-run. Everything below is reproducible from a clean clone.

1. Reproduce it yourself#

git clone https://github.com/shahvatsalofficial/archsutra-ai
cd archsutra-ai
npm ci
npm test                       # builds, then runs 20 tests
node scripts/eval.mjs          # labeled-fixture precision / recall
node dist/cli.js verify .      # validates skills, agents, links, diagrams
node dist/cli.js audit .       # the tool audits itself

3. Continuous integration#

Workflow: .github/workflows/ci.yml. Matrix: Ubuntu, Windows, macOS x Node 20, 22 = 6 jobs. Each job runs npm ci, typecheck, tests, verify, a self-audit with --fail-on high, and a check that production dependencies are empty.

Result on the release commit: all 6 jobs succeeded. Live status and history: https://github.com/shahvatsalofficial/archsutra-ai/actions

A first CI run failed on Node 20 because the test script used a glob unsupported by Node 20's test runner; the fix (use node --test auto-discovery) was committed and all 6 jobs then passed. This is a real example of CI catching a portability bug.

Additional workflows: CodeQL static analysis (JavaScript/TypeScript, weekly and on push), Dependabot, and the docs-site deploy.

4. Labeled-fixture evaluation#

Two fixtures with ground-truth expectations live in fixtures/:

FixtureDescriptionExpected rules
brownfield-monolithlayered monolith with deliberate violations (SQL interpolation, eval, disabled TLS verification, module cycle, layer inversion, root container, unpinned image, latest dependency, no lockfile, no CI/tests/README)12
clean-servicesmall well-formed service (README, lockfile, tests, CI, pinned non-root Dockerfile)0

Result (docs/proof/eval-results.json):

MetricValue
True positives12
False positives0
False negatives0
Precision1.00
Recall1.00

How to read this honestly. The fixtures were written by the rule author. This is a regression suite that proves the rules do what they were designed to do, not an estimate of real-world accuracy. Real repositories will produce false positives and false negatives. A community-contributed corpus of real, labeled repositories is a roadmap item; until then, do not quote these numbers as accuracy.

6. Self-audit (dogfooding)#

The tool audits its own repository in CI with the gate --fail-on high; on the release commit it reports no findings. Dogfooding is how two classes of false positive were found and fixed before release: rule text quoted inside generated HTML or JSON reports (TLS and IaC rules), and deliberately flawed fixture manifests (container and lockfile rules). Each now has a regression test. Command output: docs/proof/verify-output.txt.

8. What is not proven#

ClaimStatus
Skills are discovered and followed inside live Claude Code, Cursor, Codex, Copilot, Gemini CLINot verified. Only file generation is tested
Mermaid diagrams renderStructurally checked; rendering verified manually in a browser for the handbook site only
Accuracy on real-world repositoriesNot measured
Performance on very large monoreposBounded by design; no benchmark published
Any legal or regulatory complianceNot claimed

If you can verify one of these, please open a "Host smoke test report" issue.
