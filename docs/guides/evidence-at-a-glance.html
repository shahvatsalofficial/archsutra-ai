    Evidence at a glance

    The proof behind ArchSutra in five charts: accuracy on real repositories, where the first version was noisy, a sample audit, scan speed and test coverage, with plain-language caveats.

    Version 0.1.5 · Source: docs/guides/evidence-at-a-glance.md

    Claims are cheap, so here is the evidence, drawn directly from the data files in the repository. Every chart is regenerated by node scripts/build-charts.mjs, so the pictures cannot drift from the numbers. The honest limits are written under each one.

    1. Is it accurate on real code?#

    We ran the tool on 52 public repositories (Express, Django, Flask, Vue, webpack, Juice Shop, WebGoat and more) and hand-labeled 98 of its findings by reading the cited code.

    How to read it:

    • Precision is the share of findings where the code really was what the rule said. It started at 50%, which was not good enough.
    • We fixed each kind of false positive (comments, vendored files, dummy passwords, test data, wrong rule claim, and more), then measured on repositories never used for tuning: 69%, then 95% after a second round.
    • Actionable is the share a maintainer would plausibly act on. It is lower, because many real matches are intentional or low risk. This is the number to keep in mind when you triage.
    Warning. Read the whiskers. Samples are small (21 to 48 labeled findings per batch), there was a single labeler (an AI model reading each cited line, with every label published so you can challenge it), recall is not measured on real code, and part of the improvement comes from fixes designed on earlier batches. Treat "roughly 70% to 95% precision, about half actionable" as the honest range, not a guarantee.

    2. Where was the first version noisy?#

    The weak spots were exactly what you would expect from pattern matching: words like "token" in editor themes and docs, imports of package.json counted as code cycles, eval() mentioned inside comments, vendored libraries counted as huge files. Each of these has a fix and a regression test. The per-rule limits are in the rule catalog.

    4. How fast is it?#

    Measured on one Windows laptop, which is slower for file access than a Linux CI runner. Real repositories take a median of about 1.2 seconds. Scans stop at 5 000 files, and the report says when it did.

    5. How well is the tool itself tested?#

    The suite has dozens of tests across safety (path traversal, symlinks, hostile file names, pathological lines), analysis, installer behavior, report escaping and the CLI contract. Continuous integration runs it on Ubuntu and Windows with Node 20, 22 and 24, plus the newest Node on Ubuntu. macOS is not in CI because GitHub's macOS runners were unavailable.

    What is not proven#

    ClaimStatus
    Skills load and work inside each live AI IDENot verified; layouts match vendor docs; smoke-test log is empty
    Recall (finding everything that exists)Not measured on real code
    Independent security reviewNone yet; one is welcome
    Trademark clearance and lawyer reviewNot done

    The complete register of trust gaps, with status and what would close each, is in Trust and assurance. The method, every label and the reproduction commands are in the real-world evaluation.

    Reproduce it yourself#

    git clone https://github.com/shahvatsalofficial/archsutra-ai
cd archsutra-ai && npm ci && npm test
node scripts/realworld.mjs report holdout2     # the headline accuracy table
node scripts/build-charts.mjs                  # regenerate every chart on this page
