### AS-SEC-004#001 - Dynamic code or shell execution

| Severity | Confidence | Category | Effort | Owner |
|---|---|---|---|---|
| high | medium | security | M | application developer |

**Evidence**
- [observed] `src/services/user.ts:3` - `const score = eval(expr);`

**Impact:** If any input reaches these calls, an attacker can execute arbitrary code or commands.

**Why it matters:** Injection (OWASP A03) frequently starts at eval/exec style sinks.

**Fix:** Replace with a safe API (argument arrays, parsers, allowlists). Never build commands or code from strings that include external input.

**Verify:** Trace data flow into each call; add a unit test with hostile input.

**Acceptance:** No eval/Function/shell-string execution remains, or each remaining use is documented with a proven constant input.

**Caveats / false-positive notes:** Pattern match only. The call may only receive constants; confirm by data-flow review.

**References:** https://owasp.org/Top10/

### AS-SEC-005#002 - SQL built by string concatenation or interpolation

| Severity | Confidence | Category | Effort | Owner |
|---|---|---|---|---|
| high | medium | security | M | application developer |

**Evidence**
- [observed] `src/services/user.ts:2` - `const rows = await db.query('SELECT * FROM users WHERE id = ${id}');`

**Impact:** Possible SQL injection and unpredictable query plans.

**Why it matters:** Parameterized queries are the primary defence against injection (OWASP A03).

**Fix:** Use parameterized queries or the ORM query builder. Allowlist any dynamic identifiers.

**Verify:** Search for the pattern again; add an injection test (e.g. a quote character in input).

**Acceptance:** All queries with external input use bind parameters.

**Caveats / false-positive notes:** Heuristic. Interpolated values may be constants or already validated.

**References:** https://owasp.org/Top10/, https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html

### AS-SEC-006#003 - TLS certificate verification disabled

### AS-ARC-001#004 - Circular dependency between modules (src/api <-> src/db)

| Severity | Confidence | Category | Effort | Owner |
|---|---|---|---|---|
| medium | high | architecture | M | tech lead |

**Evidence**
- [observed] `src/api/routes.ts:1` - `import { findUser } from '../db/repo.js';`
- [observed] `src/db/repo.ts:1` - `import { getUser } from '../api/routes.js';`

**Impact:** Cyclic modules cannot be understood, tested, versioned or deployed independently.

**Why it matters:** Acyclic dependencies keep change local and make extraction (e.g. to a service) feasible.

**Fix:** Extract the shared concept into a lower-level module or invert one dependency behind an interface.

**Verify:** Re-run `archsutra map`; cycles list must be empty. Add the check to CI.

**Acceptance:** archsutra map reports zero module cycles.

**Caveats / false-positive notes:** Module = top-level directory heuristic; a cycle between sub-folders of one deliberate unit may be acceptable.

**References:** https://en.wikipedia.org/wiki/Acyclic_dependencies_principle

### AS-ARC-002#005 - Lower layer depends on a higher layer

| Severity | Confidence | Category | Effort | Owner |
|---|---|---|---|---|
| medium | medium | architecture | M | tech lead |

**Evidence**
- [observed] `src/db/repo.ts:1` - `import { getUser } from '../api/routes.js';`

**Impact:** Data or service code that imports presentation code inverts the intended dependency direction and blocks reuse.

**Why it matters:** Layer direction is what keeps business and data logic independent of delivery mechanisms.

**Fix:** Move shared types down, or introduce an interface owned by the lower layer and implemented above.

**Verify:** Add a dependency-direction fitness test (e.g. dependency-cruiser, ArchUnit) and run it in CI.

**Acceptance:** No import from data/service layers into presentation layers.

**Caveats / false-positive notes:** Layers are inferred from folder names (controllers, services, repositories...). Verify your real layering.

**References:** https://c4model.com/

### AS-OPS-003#008 - Container runs as root

| Severity | Confidence | Category | Effort | Owner |
|---|---|---|---|---|
| medium | high | security | S | DevOps |

**Evidence**
- [observed] `Dockerfile:1-4` - `no USER instruction`

**Impact:** A compromised process has root inside the container, easing escape and file tampering.

**Why it matters:** Non-root containers are baseline hardening.

**Fix:** Create an unprivileged user and add `USER <name>` before the entrypoint.

**Verify:** `docker run --rm image id` shows a non-zero uid.

**Acceptance:** Final image stage runs as a non-root user.

**Caveats / false-positive notes:** Some build-only stages legitimately use root; only the final stage matters.

**References:** https://docs.docker.com/build/building/best-practices/#user
